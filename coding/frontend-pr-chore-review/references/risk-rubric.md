# Frontend Chore Risk Rubric

只把能由本次前端 diff 直接证明的问题放入 `风险项`。风险类型只能是 `没有完成维护目标`、`引入了新的问题`、`代码质量问题` 或 `性能问题`。

## 没有完成维护目标

满足以下全部条件时输出：

1. 能从 PR、issue、旧配置、工程命令或生成关系证明具体的维护目标。
2. changed config/code 遗漏了实现目标所必需的声明、锁文件、脚本、CI、产物或消费方同步。
3. 能指出真实可达的命令、环境、构建、生成或发布路径，以及由分叉造成的具体结果。
4. 能给出落在本次前端范围内的维护补全方向。

常见证据包括：

- manifest、workspace 声明和 lockfile 不一致；
- source of truth 已改变，但生成产物、索引或快照没有同步；
- 本地脚本已更新，CI、缓存键、文档命令或发布入口仍使用旧路径；
- 版本或配置只更新了一处，其他真实消费方仍要求旧契约；
- 删除或重命名后仍存在可达的旧配置、产物或兼容分支。

仅仅认为版本可以更新得更多、工具选择不同或配置可以更优雅，不构成该风险。

## 引入了新的问题

满足以下全部条件时输出：

1. 问题由本次 changed frontend config/code 引入。
2. 存在真实可达的命令、环境、构建、测试、生成、发布或运行时路径。
3. 能说明新的失败、错误产物、兼容回归、验证失真或产品行为变化。
4. 该结果不是 PR 明确要求的有意变化。
5. 能给出不破坏维护目标的调整方向。

重点检查：

- 依赖分类、版本解析、peer 约束、原生模块和 postinstall 是否破坏安装或运行；
- Node、包管理器、OS、shell、浏览器和 SSR/production 环境是否分叉；
- glob、ignore、transform、mock、snapshot 或缓存是否让测试遗漏真实代码；
- codegen 输入、版本和输出是否确定且同步；
- 环境变量、tree-shaking、chunk、source map、权限和 secret 范围是否意外改变；
- 工程维护是否引入非预期的用户可见行为变化。

## 代码质量问题

满足以下全部条件时输出：

1. 本次 changed frontend code/config 命中明确适用的 Vercel React Best Practices rule。
2. 能指出真实消费或维护路径，而不只是个人工具或配置偏好。
3. 能说明不必要的耦合、重复配置、脆弱契约或运行时代码结构造成的具体维护或演进影响。
4. 能给出保持维护目标和工程不变量的可执行调整方向。

## 性能问题

满足以下全部条件时输出：

1. 本次 changed frontend code/config 命中明确适用的 Vercel React Best Practices 性能 rule。
2. 存在真实可达的构建、加载、请求、渲染或交互路径。
3. 能从代码或配置证明额外 waterfall、bundle 成本、服务端工作、请求、重渲染或计算，而不只是假设“可能更慢”。
4. 能给出不破坏维护目标的可执行优化方向。

## 输出门槛

每项风险必须包含：

- `具体说明`：触发命令或消费路径、changed config/code 和具体错误、维护或性能影响；
- `具体代码`：固定到 head commit 的 GitHub 链接和逐字核心代码或配置；
- `建议修复`：可执行的维护补全、回归消除、代码质量调整或性能优化方向。

证据不足、旧问题、个人工具偏好、格式和 nit 不输出。没有合格风险时写 `无风险项。`

Vercel subagent 的候选问题由 owner 复核并分类为 `代码质量问题` 或 `性能问题`；不满足对应全部条件时不输出。
