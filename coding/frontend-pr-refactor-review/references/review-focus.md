# Frontend Refactor Review Focus

## 规模

- `Small`：一个局部抽取或重命名，调用方有限，不改变共享状态、公共契约或持久化。
- `Medium`：跨多个组件/hooks，迁移共享状态、查询层、通用组件或多个调用方。
- `Large`：跨页面、前端包或架构边界；迁移公共契约、路由、持久化、渲染或全局状态。

公共组件/hook、认证、敏感数据、异步竞态、缓存一致性、SSR/水合、动态 import、生产依赖和性能关键路径至少提升一级审查深度。

## 不变量清单

只选择适用于当前重构的不变量，并给出旧/新证据：

- 渲染：DOM 语义、条件渲染、列表 key、布局、文本与可访问名称。
- 事件：处理顺序、传播、默认行为、快捷键、焦点和重复操作。
- 状态：初始值、派生值、更新批次、闭包、共享范围、重置与持久化。
- 副作用：依赖、执行次数、清理、取消、remount、订阅和浏览器 API。
- 请求：参数、query key、缓存、重试、错误、取消、竞态和乐观更新。
- 契约：props、context、store、事件、可空性、错误语义和序列化。
- 环境：SSR/CSR、水合、目标浏览器、动态 import 和构建产物。
- 性能：渲染次数、memo 边界、加载时机、包体积和内存生命周期。

## 迁移完整性

- 搜索全部静态 import、动态 import、re-export、注册表和字符串引用。
- 检查生产调用方、测试夹具、Storybook、mock、生成代码和示例。
- 确认旧 API 的保留、弃用或删除策略与 PR 意图一致。
- 检查新旧实现是否并存并产生状态、缓存或样式分叉。
- 删除项是否仍被运行时、构建或插件发现机制引用？

## 抽象与所有权

- 新抽象是否统一了真实共享的不变量，而不是只统一语法相似？
- API 是否比原实现更窄、更稳定、更容易正确使用？
- 状态和副作用是否仍由最清楚其生命周期的层拥有？
- 是否引入循环依赖、反向依赖、跨包泄漏或不必要的兼容层？
- 重复实现、死代码、临时 adapter 和旧测试是否按计划清理？
- 复杂度是否只是从调用方移动到更难理解的通用层？

主观上“不喜欢抽象”不是 finding。必须证明具体错误、迁移遗漏或维护风险。

## 风险叠加项

只选择最相关的最多两个：

- React 状态与副作用：闭包、依赖数组、清理、remount 和 render 更新。
- 数据请求与缓存：query key、失效、分页、重试、乐观更新和陈旧结果。
- SSR 与浏览器：水合、server/client 边界、window API 和浏览器差异。
- 可访问性：键盘、焦点、ARIA、语义、缩放和屏幕阅读器。
- 国际化与布局：长文本、复数、RTL、溢出、窄屏和动态高度。
- 契约：props、事件、可空字段、旧响应、序列化和运行时校验。
- 依赖与构建：re-export、循环依赖、tree-shaking、chunk 和生产构建。
- 性能：重复渲染、大列表、加载时机、重型依赖和尾延迟。
