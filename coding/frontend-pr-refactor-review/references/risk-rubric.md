# Frontend Refactor Risk Rubric

只把能由本次前端 diff 直接证明的问题放入 `风险项`。风险类型只能二选一。

## 没有完成重构目标

满足以下全部条件时输出：

1. 能从 PR、issue、旧实现或测试证明具体的重构目标。
2. changed logic 仍保留与该目标冲突的旧职责、重复来源、兼容路径或未迁移调用方。
3. 能指出真实可达的调用、构建或维护路径，以及目标未完成造成的具体分叉、错误所有权或后续误用风险。
4. 能给出落在本次前端范围内的迁移补全或结构调整方向。

常见证据包括：

- 部分调用方仍使用旧 API，导致新旧状态、缓存、样式或行为并存；
- re-export、动态 import、注册表、mock 或生成入口遗漏迁移；
- 旧兼容层、重复实现或死代码仍是可达路径；
- 新抽象没有承接声明的职责，调用方仍需绕过它复制同一逻辑。

仅仅认为抽象可以更优雅、文件还可以更少或命名可以更好，不构成该风险。

## 引入了新的问题

满足以下全部条件时输出：

1. 问题由本次 changed frontend code 引入。
2. 存在真实可达的用户、浏览器、渲染、调用或构建路径。
3. 能说明被改变的渲染、事件、状态、请求、副作用、契约、性能或可访问性结果。
4. 该结果不是 PR 明确要求的有意变化。
5. 能给出不破坏重构目标的调整方向。

重点检查：

- 抽取后条件、默认值、事件顺序或错误语义是否改变；
- 状态所有权、闭包、依赖、清理、取消和 remount 生命周期是否改变；
- 请求参数、query key、缓存、重试和竞态处理是否改变；
- props、context、store、re-export 和可空性契约是否被破坏；
- SSR/水合、动态 import、tree-shaking、焦点、键盘和布局是否回归。

## 输出门槛

每项风险必须包含：

- `具体说明`：触发条件、changed logic 和具体错误或分叉结果；
- `建议修复`：可执行的迁移补全、结构调整或回归消除方向。

证据不足、旧问题、个人偏好、格式和 nit 不输出。没有合格风险时写 `无风险项。`
