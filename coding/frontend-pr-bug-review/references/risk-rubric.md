# Frontend Bug Risk Rubric

只把能由本次前端 diff 直接证明的问题放入 `风险项`。风险类型只能是 `没有从根因修复`、`引入了新的问题`、`代码质量问题` 或 `性能问题`。

## 没有从根因修复

满足以下全部条件时输出：

1. 能从 issue、测试、旧实现或调用链证明真实根因。
2. changed logic 位于症状层、局部调用方或错误恢复层，没有消除根因。
3. 能指出原问题仍会触发的真实输入、状态、时序或相邻调用路径。
4. 能给出落在本次前端范围内的根因修复方向。

常见证据包括：

- 只吞掉异常、忽略失败或隐藏错误 UI；
- 只强制刷新、重置状态、扩大重试或增加局部 guard；
- 共享层根因仍存在，只修复了一个入口；
- 旧缓存、旧数据、快速切换或另一个调用方仍能绕过修复。

仅仅认为“可以写得更优雅”不构成该风险。

## 引入了新的问题

满足以下全部条件时输出：

1. 问题由本次 changed frontend code 引入。
2. 存在真实可达的用户、浏览器或渲染触发路径。
3. 能说明新的错误 UI、状态、请求、副作用、性能或可访问性结果。
4. 该结果不是 PR 明确要求的有意变化。
5. 能给出不破坏原 Bug 修复目标的调整方向。

重点检查：

- 正常路径是否被新 guard、默认值或条件分支误伤；
- 状态、缓存、重试、取消和卸载生命周期是否改变；
- 共享组件或 hook 的其他调用方是否回归；
- loading、empty、error、权限、键盘、焦点、长文本和窄屏是否出现新问题；
- 回归测试是否只覆盖 mock，而真实运行时数据仍会失败。

## 代码质量问题

满足以下全部条件时输出：

1. 本次 changed frontend code 命中明确适用的 Vercel React Best Practices rule。
2. 能指出真实消费或维护路径，而不只是个人风格偏好。
3. 能说明不必要的状态、副作用、耦合、重复逻辑或脆弱契约造成的具体维护或演进影响。
4. 能给出保持 Bug 修复目标的可执行调整方向。

## 性能问题

满足以下全部条件时输出：

1. 本次 changed frontend code 命中明确适用的 Vercel React Best Practices 性能 rule。
2. 存在真实可达的加载、请求、渲染、交互或构建路径。
3. 能从代码证明额外 waterfall、bundle 成本、服务端工作、请求、重渲染或计算，而不只是假设“可能更慢”。
4. 能给出不破坏 Bug 修复目标的可执行优化方向。

## 输出门槛

每项风险必须包含：

- `具体说明`：触发或消费路径、changed logic 和具体错误、维护或性能影响；
- `具体代码`：固定到 head commit 的 GitHub 链接和逐字核心代码；
- `建议修复`：可执行的根因修复、回归消除、代码质量调整或性能优化方向。

证据不足、旧问题、个人偏好、格式和 nit 不输出。没有合格风险时写 `无风险项。`

Vercel subagent 的候选问题由 owner 复核并分类为 `代码质量问题` 或 `性能问题`；不满足对应全部条件时不输出。
